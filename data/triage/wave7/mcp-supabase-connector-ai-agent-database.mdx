An AI agent with a persistent database remembers clients, bookings and campaign numbers between sessions because the data lives in Supabase rather than in the chat window. You connect the agent through the Model Context Protocol (MCP), create a small set of tables, and limit what the agent can touch using separate keys and row-level security. This guide covers the setup, a schema for a local business, a worked time estimate, and the guardrails to put in place before the agent writes data.

## Why does an AI agent forget your clients between sessions?

A chat session holds context only while it is open. When the window closes, the model starts from its training and whatever you paste in next. Each request is handled on its own, so a booking made on Monday is not available on Thursday unless something outside the chat stored it.

That gap is why the first week with an AI assistant often feels productive and the second week feels like repeat work. You re-explain services, prices and regular customers every time. The fix is not a longer prompt. It is an external store the agent can query at the start of each task, so the context comes from your data instead of your memory.

## What should the database hold for a local business?

Four tables cover most local workflows: clients, appointments, reviews and marketing metrics. Keep the list short. Each table should answer a question you ask every week, such as which clients are due for a rebooking or which campaign produced bookings last week.

- clients: name, phone, preferred service and notes
- appointments: service, staff member, start time, status and price
- reviews: platform, rating, text and whether you replied
- marketing_metrics: weekly spend, clicks, bookings and revenue by campaign

Booking workflows such as those in [AI agent for appointment booking for local businesses](/blog/ai-agent-for-appointment-booking-local-business) depend on the appointments table being accurate. Define the status values, such as confirmed, completed, cancelled and no-show, before you write any code, so the agent does not invent its own labels.

## How do you connect Supabase to an AI agent through MCP?

Work through these steps in order and do not give the agent write access until the read test passes.

1. Create a Supabase project and note the project URL. Store the service role key in a password manager, not in a shared document.
2. Install the Supabase MCP server package, using the current package name from Supabase's MCP documentation, since package names change.
3. Add the server to your MCP client's configuration file, passing the URL and key as environment variables.
4. Restart the client and confirm the Supabase tools appear before asking the agent to change anything.
5. Run one read-only test, such as counting rows in the clients table, and check the answer against what you see in the dashboard.

A typical configuration entry looks like this, with placeholders replaced by your own values:

```json
{
  "mcpServers": {
    "supabase": {
      "command": "npx",
      "args": ["-y", "@supabase/mcp-server-supabase"],
      "env": {
        "SUPABASE_URL": "YOUR_SUPABASE_URL",
        "SUPABASE_SERVICE_ROLE_KEY": "YOUR_SUPABASE_SERVICE_KEY"
      }
    }
  }
}
```

Keep the key away from anywhere the agent does not need it. Cursor's changelog describes build secrets in its cloud agent environments as scoped to the build step and not passed to the running agent's environment ([Cursor changelog](https://cursor.com/changelog/05-13-26)). The same principle applies here: the agent gets the access its task requires, and nothing more.

## How do you stop the agent from reading every client's record?

Use two keys with two jobs. The service role key belongs to your own server-side agent, which needs full access to do its work. A client-facing chatbot on your website should never receive that key. It should run with a restricted role, and row-level security policies should limit it to rows that belong to the person chatting.

Enable row-level security on the clients and appointments tables before you load real names and phone numbers. Then test the policy from the restricted role by requesting another client's record. If a row comes back, the policy is wrong and the chatbot should stay offline until it is fixed. Write the policy against your own authentication setup, because a policy that depends on a claim the chatbot never receives will simply block everything, which is a different failure but still a failure.

## What guardrails should come before the agent writes data?

Write access deserves the same slow start you would give a new hire. The author of HubSpot's article on AI agents for social media recommends manually approving every agent post for the first one to two months before letting the agent act on its own ([HubSpot](https://blog.hubspot.com/marketing/ai-agents-for-social-media)). Apply that pattern to database writes: have the agent propose each booking or metric update, review the proposals for a few weeks, and only then allow direct inserts.

## How much time does persistent memory save?

The estimate below uses assumed inputs, so replace them with your own numbers before deciding anything. The point is to show the arithmetic behind the time you lose to re-briefing.

Inputs, all assumptions:
- Re-briefings per week: 10
- Minutes to re-explain services, prices and regulars: 4
- Weeks per month: 4.33
- Value of your time: $30 per hour

Calculation:
- Minutes per week: 10 × 4 = 40
- Minutes per month: 40 × 4.33 = about 173 (roughly 2.9 hours)
- Monthly value: 2.9 × $30 = about $87

At these assumed inputs, persistent memory returns about $87 of owner time per month. Subtract the hours you spend on setup and the cost of your database plan, which you should check on Supabase's current pricing page, since this article does not quote plan limits. If your staff each re-brief the agent separately, the saving grows with the number of people, so run the same calculation for each person who uses the agent.

## FAQ

### Do I need to know SQL to run this setup?

Basic SQL helps but is not strictly required. The Supabase dashboard includes a table editor for creating tables without writing statements. Basic knowledge of SELECT, INSERT and WHERE is still useful, because it lets you check what the agent actually ran when a result looks wrong.

### Can several AI agents share one Supabase project?

Yes. A booking agent, a reporting agent and a review agent can all read from the same database, so they work from the same client records. Give each agent its own credentials where possible, so you can tell from the logs which one made a change.

### What happens if the agent writes a wrong record?

Stop the agent first, then find the record and correct it. Keep the proposal-and-approval stage running until the errors stop, and check your backup and recovery options on your plan before you give the agent direct write access.

### Should I store full review text in the database?

You can, and it helps the agent find patterns across reviews. If your review text is long or you export it often, keep the full text in the database but link to the original review on the platform, so you do not have to maintain two copies that can drift apart.
