A Claude booking agent for Google Calendar needs three parts: a Google Cloud project with the Calendar API enabled, a way for Claude to call your calendar, and rules for what the agent may book. Claude can reach the calendar through an MCP server or through tools you define yourself. Both work. Which one fits depends on where your code runs.

This guide is for owners of appointment-based shops and the developers who help them. It follows Anthropic's and Google's documentation as opened on 6 November 2026. The code is an outline built from those docs. It has not been run against a live calendar, so test it on a spare calendar first.

## Should You Use MCP or Your Own Tools?

Anthropic's MCP connector lets the Messages API call a remote MCP server without a separate MCP client. Its documentation lists two limits that matter here: only tool calls are supported from the MCP specification, and the server must be publicly exposed over HTTP (Streamable HTTP or SSE). Local STDIO servers cannot be connected directly. The connector is in beta and uses the `mcp-client-2025-11-20` beta header, with an `mcp_servers` entry plus a matching `mcp_toolset` in `tools`.

So if you already run a Google Calendar MCP server at a public HTTPS address, the connector saves code. If you do not, defining two tools of your own is simpler and keeps credentials inside your server. Anthropic's tool docs describe a user-defined tool as a `name`, a `description` and an `input_schema` in JSON Schema.

For a deeper comparison of servers, see our [guide to MCP servers for local business](/blog/best-mcp-servers-local-business-setup-guide) and the walkthrough on [building a custom MCP server](/blog/build-mcp-server-custom-data-local-business).

## What Do You Need Before You Start?

1. A Google Cloud project with the Google Calendar API enabled and OAuth credentials.
2. An Anthropic API key from the Claude Console.
3. A calendar the agent may write to. Use a separate booking calendar for testing.
4. A server that holds the credentials and runs the code below. Do not put keys in a web page.

Choose the narrowest Calendar scope. Google's scope list includes `calendar.app.created` (create secondary calendars and manage events on them only), `calendar.events.owned` (events on calendars the user owns), `calendar.events` and the full `calendar`. Google's page advises choosing "the most narrowly focused scope possible". For a booking agent that writes only to a dedicated calendar, `calendar.app.created` is the narrowest match. For reading free time on an existing calendar, the `calendar.events.freebusy` scope is listed as valid for the free/busy query.

## How Does the Agent Check Availability?

Google's `freeBusy.query` method is a POST to `https://www.googleapis.com/calendar/v3/freeBusy`. The body needs `timeMin`, `timeMax` and `items` (each calendar `id`). Optional `timeZone` defaults to UTC, so always set it to the shop's zone. The response lists `busy` intervals per calendar. Free time is whatever is left inside your opening hours.

```python
from googleapiclient.discovery import build

def busy_blocks(creds, calendar_id, time_min, time_max, tz):
    service = build("calendar", "v3", credentials=creds)
    body = {
        "timeMin": time_min,   # RFC3339, e.g. 2026-11-12T09:00:00-06:00
        "timeMax": time_max,
        "timeZone": tz,        # e.g. America/Chicago
        "items": [{"id": calendar_id}],
    }
    result = service.freebusy().query(body=body).execute()
    return result["calendars"][calendar_id]["busy"]
```

Your code, not Claude, should subtract busy blocks from opening hours and service length, then return a short list of open slots. Keeping that arithmetic out of the model avoids double-booking mistakes.

## How Does It Create the Booking?

`events.insert` posts to the events path of a single calendar. Google lists `start` and `end` as the required properties, and the `end` time is exclusive. The `sendUpdates` parameter takes `all`, `externalOnly` or `none`. Google warns that `none` can stop events from syncing to external calendars for some users, so use `all` when you add the customer as a guest.

```python
def create_booking(creds, calendar_id, summary, start_iso, end_iso, tz, guest_email=None):
    service = build("calendar", "v3", credentials=creds)
    event = {
        "summary": summary,
        "start": {"dateTime": start_iso, "timeZone": tz},
        "end": {"dateTime": end_iso, "timeZone": tz},
    }
    if guest_email:
        event["attendees"] = [{"email": guest_email}]
    return service.events().insert(
        calendarId=calendar_id, body=event, sendUpdates="all"
    ).execute()
```

Re-check the slot with a fresh free/busy call immediately before inserting. Two customers can ask for the same hour within seconds.

## How Do You Give Claude These Two Functions?

Define each function as a tool. A minimal availability tool looks like this, following the schema fields in Anthropic's docs:

```json
{
  "name": "get_open_slots",
  "description": "Returns open appointment start times for one service on one date at this shop. Use it before offering times to a customer. It does not book anything. Dates are YYYY-MM-DD in the shop's local time.",
  "input_schema": {
    "type": "object",
    "properties": {
      "date": {"type": "string", "description": "Date to check, YYYY-MM-DD"},
      "service": {"type": "string", "enum": ["haircut", "colour", "consultation"]}
    },
    "required": ["date", "service"]
  }
}
```

A second tool, `book_slot`, takes a start time, service, customer name and email. Anthropic's docs say Claude's reply contains `tool_use` blocks and you send results back as `tool_result` blocks in the next request. Your server runs the Google call in between and returns only the fields Claude needs, such as the open times or a confirmation.

Anthropic's tool guidance stresses detailed descriptions: what the tool does, when to use it and what it returns. Write them that way. Keep the model out of the calendar credentials entirely.

## What Should the Agent Never Do?

- Book outside opening hours or without a service length.
- Cancel or move an existing appointment without a human check.
- Quote prices or promises that are not in its instructions.
- Store card details. Take deposits through your payment provider.

Log every booking with the customer's request text so you can audit mistakes. If your shop already uses a booking app, compare it with this build first. ## Worked Example: Is It Worth Building?

All numbers are **assumptions**, not measurements.

| Input | Assumption |
| --- | --- |
| Booking requests handled by hand per week | 15 |
| Minutes of back-and-forth per request | 5 |
| Weekly time spent | 15 x 5 = 75 minutes |
| Hourly value of owner time | $30 |
| Weekly value | 75 / 60 x $30 = $37.50 |

At those inputs the build saves about $37.50 a week of owner time, before model, hosting and developer costs, which depend on your setup. If the agent also catches bookings that would otherwise go to a competitor, that is extra, but you need your own data to know how many. Start with two weeks of tracking: count requests, response time and bookings lost.

## FAQ

### Do I need MCP to connect Claude to Google Calendar?

No. MCP is one option. Anthropic's connector needs a publicly reachable remote MCP server over HTTP. You can instead define your own tools and call the Google Calendar API from your server.

### Which Google Calendar scope should a booking agent use?

Use the narrowest scope that works. Google lists `calendar.app.created` for calendars your app creates and `calendar.events.owned` for events on calendars the user owns. Broader scopes like `calendar` expose more data.

### What are the Google Calendar API limits?

Google's quota guide lists 10,000 requests per minute per project and 600 per user per project. Exceeding them returns HTTP 403 or 429, and Google recommends exponential backoff.

### Can Claude double-book a slot?

Only if your code lets it. Do the availability arithmetic in code and re-check free/busy right before inserting the event.

### Is the MCP connector stable?

Anthropic marks it as beta, with a dated beta header. Check the current docs before relying on it in production.
